# 规则引擎规格

> 校验段是纯规则引擎（零 LLM），「LLM 产出 + 规则校验」是本作品的工程卖点。
> 实现见 `server/agent/validator.py`；每条规格都能在 `tests/test_validator.py` 与
> `tests/test_severity.py` 找到对应用例。

## 一、五条规则总表

| 规则 | severity | 判定条件 | 阈值 | 修复策略 | fix_hint |
|---|---|---|---|---|---|
| V1 时长 | **hard** | 内容时长超容量 或 收班超时 | 见容量口径 | 摘点（非必游优先） | drop |
| V2 开放窗口 | **hard** | 到/离时间落在 `open_hour` 之外 | — | 移除该点 | drop |
| V3 强度 | **soft** | `Σ(slope + crowd_level×0.4) > 8.5` | 8.5 | **不自动修复**——发 `advisory` 提醒，决策权交还用户 | none |
| V4 预算 | **hard** | 门票+餐饮+交通 > 用户预算 | 请求值 | 摘高票价点（非必游优先） | drop |
| V5 亲子 | **hard** | 亲子模式下 `family < 2` 的点入选 | 2 | 移除该点 | drop |

**软硬分级的语义**（prompt 01B 引入）：
- `hard`：进入「违规回流修复」循环（见下文），必须自动修复
- `soft`：只发 `validate/advisory` 事件，**不占硬违规的名额、不进循环**——
  强度没有唯一正确的删点解，系统如实提示、把决策权交还用户
- 「校验通过」只看 hard：`pass` 事件的 reason 写「硬约束零违规；另有 N 条软提醒（已如实标注）」

## 二、容量口径（V1 的核心不变量）

```
容量 cap  = (DAY_END 22:00 - DAY_START 8:30 - 午晚餐 2h - 缓冲 0.5h) - (跨城日再扣城际 1.8h)
         = 11.0h（同城日） / 9.2h（跨城日，如 Day3 成都→重庆）

内容 content = Σ(leg_hours + visit_hours)    ← 相邻跳口径，leg 从城市枢纽起算
收班         = 最后一个点的 departure ≤ 22:00
```

**规划器与校验器必须同口径**（prompt 01B 修掉的 D1 同类 bug）：
- 历史教训：规划器装箱曾用**质心跳**估交通（乐观），校验器用**相邻跳**（真实），
  两把尺子差 1.5% → 换参数即触发 V1 误报
- 现状不变量：`planner._content_hours()` 与 `validator` 的 `content_hours`
  都是相邻跳、都从 `CITY_HUB`（meta.json）起算——参数化测试
  `test_v1_zero_false_positive`（5 组参数）守护这条不变量
- 跨城日的城际 1.8h **只在容量里预留，不在 span 里重复扣**（prompt 01 修掉的 D1 根因）

**违规文案格式**：`[rule] 第N天` + 一句中文说明，detail 区分两种超标：
- 收班超时：`收班超时：22.25h 结束超过 22:00`
- 内容超容：`内容时长 11.5h 超过容量 11.0h`

## 三、修复循环（回流 + 收敛检测）

```
校验 → 有 hard 违规？ ──否──→ pass（软提醒以 advisory 事件伴随输出）
        │是
        ▼
   fix() 定向修复（摘点/移除）→ 重新校验
        │ 新 hard 违规集合与上轮完全相同？（收敛检测）
        │──是──→ unfixable 事件：该违规无可用自动修复策略，修复后状态未变，已停止重试
        ▼
   最多 3 轮；轮满仍残留 → 如实标注，前端高亮提示
```

**收敛检测**（prompt 01B）：违规签名集合 `(rule, day, poi)` 与上轮相同 = fix 是 no-op →
立即跳出，绝不重复空转（旧版同一违规文本重复 3 遍的演示缺陷已根治）。

## 四、摘点排序键

```
(score, must_see, night_friendly)   ← 升序，元组比较
```

- **低分先摘**：偏好打分低的点价值最低
- 同分时 **非必游先摘**（`must_see=False` 排前）
- 再同分 **非夜间先摘**：夜间点是压轴体验（洪崖洞/南山一棵树），最后摘
- **不允许摘光**：`len(kept) > 1` 守护

历史教训（prompt 01C 修掉的潜伏 bug）：旧键 `(score, not must_see, not night_friendly)`
在升序下 `not True=False=0` 排最前 → **必游点与夜间点反而最先被摘**，与规格完全相反。

## 五、强度惩罚的豁免规则（装箱阶段，非校验）

```
gain -= 0.25 × (slope + crowd_level × 0.4)    ← 仅当该点 非必游 且 非夜间
```

- 强度惩罚是**软约束**，不得挤掉硬期待：必游地标（must_see）与夜间体验点（night_friendly）豁免
- 理由：「因为坡陡所以不去看夜景」是荒谬的产品决策（prompt 01C 恢复南山一棵树的教训）
- 距离惩罚 `-2.0×leg` 与夜间加分 `+0.8` 不变

## 六、每条规则的可运行示例

默认场景 `python cli.py --days 3 --budget 3000 --tags 美食,文化` 真实输出：

**V3 soft（默认场景触发）**——advisory 而非 violation：
```
 #017 [validate] ⚠ [V3-intensity] 第3天
      └ 因为 强度 12.2 超过 8.5；强度是软约束，自动删点会误伤必游地标，故保留行程并提示
 #018 [validate] ✔ 第1轮校验通过
      └ 因为 硬约束零违规；另有 1 条软提醒（已如实标注）
```

**V2 hard（夜景场景触发）**——`python cli.py --days 2 --budget 2000 --tags 夜景`：
```
 #016 [validate] ✗ [V2-open-window] 第1天
      └ 因为 排 19.0-20.5h 但开放 19-23h（九眼桥夜游最早 19:00 后到访受限场景构造）
 #018 [plan    ] ↻ 第1天移除 九眼桥·锦江夜游
      └ 因为 开放时间冲突：...
 #022 [validate] ✔ 第2轮校验通过        ← 回流修复生效
```
