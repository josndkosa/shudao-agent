## 接下来是几个具体的问题

### 一、前端把管线跑了两遍

`static/js/main.js` 里，`run()` 先 `await api.plan(req)`，然后又 `await api.stream(req, ...)`。
两个端点各自都会把三段式管线完整跑一遍。

在线模式下这就是**DeepSeek 成本翻倍**，而且更麻烦的是：**这两次是两次独立的 LLM 调用**
（temperature 0.3，我们自己在 v1.1.6 里就记录过这个非确定性 —— 同一请求跑两次，一次排三城、
一次全排成都）。于是 `state.itinerary` 来自第一次、事件流来自第二次，
**行程卡和回放事件描述的可能是两个不同的行程**。

离线模式因为结果确定，看起来完全正常 —— 这就是它一直没被测出来的原因。

我建议改成**只跑一次**：前端只调 `api.stream`，行程随事件流一起回来（可以放在结束事件里带
`itinerary` 字段）。这样在线省一半 token，而且行程和事件流**必然同源**。

要注意的是 `plan_id` 现在是从 `/api/plan` 的返回值里拿的，而 `/api/revise` 依赖它 ——
改完必须确认"对话式改行程"还能正常工作，那是 30 分功能完备度要展示的东西。

如果这条改起来动静太大，退一步的做法是让 `/api/stream` 接受一个可选的 `plan_id`，
从 `_PLANS` 缓存里把已经算好的 bus 重放一遍，不重跑管线。但这个方案在多 worker 部署下
缓存可能 miss，得留个兜底（miss 时退回重跑）。**你选方案，我不挑，但单跑这件事必须做。**

### 二、`/api/plan` 在 async 函数里同步跑管线

`server/app.py` 里 `@app.post("/api/plan")` 是 `async def`，里面直接 `run_pipeline(...)`，
既没 await 也没进线程池。`/api/stream` 已经用了 `run_in_executor`，`/api/plan` 没有。

后果是：在线模式下 `run_pipeline` → `llm.chat()` 是阻塞 HTTP 调用（有 30 秒超时了，但还是很长），
**一次请求最长能占住事件循环 30 秒**，其他所有请求全部排队。

改成 `await asyncio.to_thread(...)` 就行 —— 这是 Python 3.9+ 的标准库，
我们的 `requires-python` 是 >=3.10，**不用引任何新依赖**。

我想要一条测试证明它真的并行了：并发打两个 `/api/plan`（一个在线一个离线），
断言离线的那个能在 1 秒内返回、不被在线那个拖住。

### 三、`load_city_pois` 的城市映射得改成自动的

`server/tools/poi_search.py` 现在是这样：

```python
fn = {
    "成都": "chengdu.json", "重庆": "chongqing.json", ...
}.get(city)
if fn is None:
    # 泛化路径：城市名转拼音文件名的映射不在本层维护，未收录城市返回空
    return []
```

**它自己的注释就承认做不到这件事。** 而 `docs/开发指南.md` 里承诺了"新增城市零代码改动"——
这句话在 `load_city_pois` 这条路径上是假的（`load_pois()` 已经是自动 glob 的，只有它不是）。

好在不用多写什么：每个 POI 数据里都有 `"city": "阆中"` 这样的字段，扫一遍数据文件就能建索引：

```python
@lru_cache(maxsize=1)
def _city_file_map():
    """城市 → 数据文件名：扫数据文件的 city 字段自动建索引（新增城市零代码改动）。"""
    m = {}
    for fn in sorted(DATA_DIR.glob("*.json")):
        if fn.name == "meta.json":
            continue
        try:
            pois = json.load(open(fn, encoding="utf-8"))
        except Exception:
            continue
        for p in pois:
            if p.get("city"):
                m.setdefault(p["city"], fn.name)
                break
    return m
```

`load_city_pois(city)` 改成查这个 map 就行。这活儿大概一刻钟，但它是我们对外承诺的唯一
兑现方式 —— 而且做完之后，"加一个城市"就真的只是"放一个 json 文件"了。

### 四、首页那四个数字得改成动态的

`static/index.html` 第 26 到 29 行现在硬编码着 101 / 6 / 3 / 23。

「23」这个数字**是错的** —— 03E 批次 1 的在线实测事件流是 67 条，离线 3 天是 56 条。
这个数字从 W1 时代就没更新过。评委点开回放抽屉数一数，就会发现对不上。

POI 数和城市数其实现成的：`/api/meta` 已经返回 `{"cities": [...], "tags": [...],
"meta": {"source": "local-snapshot", "count": N}}`，前端调一下就有。

"决策事件可回放"这个数字我建议**直接删掉数字**，改成"每一步决策都可回放"这类不含数字的表述 ——
它本来就随用户输入变，写死必然对不上，`/api/meta` 里也没有这个数。

另外注意降级：后端没起的时候（本地演示模式），这四个卡片不能变成空白或者 `undefined`。
失败的时候显示"—"，或者保留一个**明确标注是"离线快照"的静态值**，但别显示一个可能已经过时的
具体数字。

### 五、公网上得加基本防护

现在 `/api/plan`、`/api/stream`、`/api/revise` 都没有鉴权、没有限流，
`message` 字段也没有长度上限（`PlanRequest` / `ReviseRequest` 上只有类型约束）。

ECS 上公网开放之后，**任何人都能无限调我们的 `/api/plan`**，在线模式下这就是直接烧我们的
DeepSeek 额度。`/api/revise` 的 `message` 还能传一个 1MB 的字符串进来。

我想加三样，**全部零新依赖**：

**输入长度上限** —— pydantic v2 原生支持，在 `PlanRequest` / `ReviseRequest` 上加
`Field(..., max_length=N)` 就行。`tags` 限项数、`message` 限 500 字符左右、`cities` 限项数。

**IP 限流** —— 用 `request.client.host` 加一个进程内的滑动窗口计数，每秒 N 次超了就返回 429。
用标准库 `time` 就够，**不要引 fastapi-limiter**。进程内限流在多 worker 下是 per-worker 的，
这没关系（下一条就说这个）。

**在线模式开关** —— 加一个环境变量（比如 `SD_ALLOW_ONLINE=1`）才允许 `mode == "online"`，
默认关闭。这样公网上别人用我们的服务只会跑离线分支，**烧不到额度**。
答辩现场要开这个开关，`readme` 的部署步骤里写清楚就行。

### 六、`_PLANS` 是进程内内存，多 worker 会让"改行程"直接 404

`_PLANS` 是个 `dict`，FIFO 上限 50，**存在进程内存里**。

如果 ECS 上用 gunicorn 或者 uvicorn 多 worker 部署，`/api/plan` 在 worker A 里算出的计划，
`/api/revise` 被负载均衡到 worker B 的时候，`plan_id` 就找不到 —— **"对话式改行程"在云上直接失效**。
这是 30 分功能完备度要展示的功能，答辩现场演它崩掉很致命。

至少要在 `readme/README.md` 的 ECS 部署章节和 `docs/华为云接入说明.md` 里写明
**必须用 `uvicorn --workers 1`**，并说明原因。改成文件或 sqlite 存储（标准库就够）也行，
但那要更多时间，先把文档写清楚。

顺带说一句，这事写进文档反而是加分的 —— 它不是缺陷，是**架构取舍**：我们把计划缓存放在进程内
是为了"零依赖、单机可跑"，代价就是单 worker。**能把代价说清楚，比假装没有强。**

在 `_normalize_llm_plan` 里加跨天去重（同 id 只留第一次，丢弃的时候发个事件说明）；
另外某天一个合法点都没剩的时候，**必须发事件**，不要静悄悄地 `continue` 掉一整天 ——
"取消一整天的行程"是重大决策，得让人看见。

**D 是回归锁。** 写到 `tests/test_event_contract.py`，六条：

1. 工具结果长度锁 —— `exec_tool("poi_search", {...})` 序列化后长度 < 3000

5. 四集合一致性锁 —— `meta.city_info` 的城 == 有数据文件的城 == `CITY_HUB` 的城

## 验收标准

我是按"评委打开 zip"来写的，所以这几条都要能当场验证：

**功能与一致性**

- `python scripts/ctl.py ci` 三连全绿，pytest 至少 90 个（现在 84，加上这六条新的），
  冒烟至少 18 步
- 一次"开始规划"只跑一次管线 —— 事件流里 `plan` 阶段的 start 只有一条
- 在线模式下行程卡和事件流同源：事件流里每个"第 N 天选点"的 poi_id 集合，
  必须都在行程单第 N 天的 poi_id 集合里
- `/api/revise` 改完之后还能正常用
- 四层口径一致，`git status` 里没有未跟踪的 `server/data/*.json`
