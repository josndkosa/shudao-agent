## 一、背景：这三个缺陷只有真跑才会暴露

v1.1.6 的在线模式首次真实运行（`mode:online`，事件流 67 条）暴露了三个缺陷。
**它们在离线路径上永远测不到**，因为离线路径没有"模型会补全残缺内容"这个行为。

### 缺陷 A（P0）· 工具结果被截断，模型编造 POI

**现象**：事件流出现「丢弃 5/6/6 个非法 POI」；贵阳市整天从行程里消失（3 城变 2 城）；
大理某天 7 个 POI 掉了 6 个只剩 1 个。

**根因（已逐行定位，不要重新猜）**：

```
planner.py:456   exec_tool 的 poi_search 分支 → return poi_search(**args)
                  返回完整 dict（13 个厚字段 + _score + _reasons）
planner.py:488   "content": json.dumps(result, ensure_ascii=False)[:4000]
                  一个 POI ≈ 300–400 字符，12 个点 ≈ 4200 > 4000
                  → 截断落在 JSON 结构中间
                  → 模型收到残缺 JSON，只能猜后面的内容 → 编造 POI id
planner.py:410   if pid in POI_INDEX → 判非法 → 丢弃
planner.py:417   if not day_pois: continue → 该整天被静默丢掉
```

**铁证**：`planner.py:30` 的 `_poi_brief()` 就是为此写的精简格式，
但**全项目只有定义处一个命中——写了从未接上**。这是"写好了但忘了用"的工程事故。

### 缺陷 B（P0）· 收尾无条件补「晚餐」，且餐数口径与负载不一致

`planner.py:221-223`：

```python
if not dinner and items:
    items.append({"type": "meal", "label": "晚餐", ...})   # 不判断当前时间
```

实跑出现「某天只有 1 个点、12:55 结束 → 晚餐 12:55–13:55」。

另：午餐只在「下一个 POI 到场时间 > 12:00」时才插入（`planner.py:204-207`），
所以中午前结束的半天**没有午餐条目**，但 `_day_load` 固定加 `MEAL_HOURS = 2`
→ **时间线只有 1 餐、负载按 2 餐算，口径不一致**。

⚠️ `_build_timeline` 是**离线路径共用**的，改动必须跑全量回归。

### 缺陷 C（P0）· 在线路径缺跨天 POI 去重 + 静默丢天无事件

实跑事件「移除 大理古城 / 崇圣寺三塔」，但最终行程的**另一天又出现了这两个点**
——模型把同一批点同时放进了多天，而 `fix()` 只作用于被报违规的那一天。

离线路径靠 `planner.py:309-311` 的 `pools[city].remove(p)` 天然去重，**在线路径没有**。

且 `planner.py:417` 整天被丢弃时**没有任何事件说明**——「取消一整天的行程」是重大决策，
必须有事件 + reason（这是本作品「每条决策带 reason」的内核）。

## 三、任务清单（按顺序做）

### 任务 A · 修工具结果截断（缺陷 A）

1. `planner.py` 的 `exec_tool` 里 `poi_search` 分支改为**返回精简格式**：

   ```python
   if name == "poi_search":
       r = poi_search(**args)
       return {"count": r["count"], "pois": [_poi_brief(p) for p in r["pois"]]}
   ```

   12 个点 × ~120 字符 ≈ 1450 字符，不再超限。**`_poi_brief` 必须真的被调用。**

2. `server/agent/llm.py` 的 `TOOL_SCHEMAS` 里 `poi_search` 增加 `limit` 参数（integer），
   description 写明「返回按 score 降序的前 N 个候选」；`exec_tool` 透传该参数。
   若模型传了 limit，`_poi_brief` 结果再截前 N 个。

3. `planner.py:488` 的 `[:4000]` 改为**在 JSON 安全边界截断**——即先 `json.dumps`，
   超长时对**列表元素**做整段丢弃后重新序列化，**绝不允许截在 JSON 中间**。
   注释里写明这条事故的根因（残缺 JSON 会被模型「补全」成幻觉）。

4. **确认 `poi_search` 工具 schema 里把 POI 的关键字段都暴露给模型**：
   `id / name / city / tags / ticket / visit_hours / open_hour / score / reasons`
   （`_poi_brief` 已经全有，不要再精简掉 `open_hour`——V2 开放窗口校验要用）

### 任务 B · 修晚餐标签与餐数口径（缺陷 B）

   中午前结束的半天**不插晚餐**。
2. 午餐逻辑（`planner.py:204-207`）保持不变，但要保证**任何一天至少有一个餐条目**
   （若当天在 12:00 前结束，补一个「午餐」）。
3. `_day_load` 的 `MEAL_HOURS` 不要再写死 2，改为**按该天时间线里实际出现的餐条目数计算**
   （或让 `_day_load` 接收实际餐数）。**关键：负载口径与时间线口径必须一致**，
   且**校验段 `content_hours`（不含餐）的口径不要动**——两把尺子各自的口径要在
   `docs/规则引擎规格.md` 里写清楚。
