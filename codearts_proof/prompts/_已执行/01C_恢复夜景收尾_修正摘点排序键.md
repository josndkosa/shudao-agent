## 问题 1（必须修）：强度惩罚把「南山一棵树」挤掉了 → Day 3 没有夜景收尾

### 现象

`docs/baseline/baseline-cli-3d.txt`（01B 后）里 Day 3 只有 3 个点：

```
10:21 ─ 湖广会馆 ¥30
13:00 ─ 磁器口古镇（3.0h）
16:39 ─ 洪崖洞（2.0h）
18:39 ── 晚餐 ──          ← 全天到此结束，没有任何夜景时段
```

01B 之前（4 个点）：

```
16:39 ─ 洪崖洞（2.0h）
18:00 ── 晚餐 ──
19:00 ─ 南山一棵树观景台 ¥30（1.5h）   ← 经典夜景机位，夜景收尾
```

### 为什么这是**演示级**问题，不只是"少一个景点"

Day 3 的叙事文案（`narrator._template_narrate`）会写：

> 「行程以夜景收尾，记得提前给相机充满电。」

而现在当天**没有任何落在夜间的景点**（洪崖洞排在 16:39–18:39，是亮灯前的下午）。
**文案与行程自相矛盾，评委一眼能看出来。**

同时，作品名叫"蜀道智行"、数据里有 `night_friendly` 字段、
南山一棵树是 `must_see: true` 的经典夜景机位——**丢掉它等于丢掉重庆的夜。**

### 根因

`_pick_day_pois()` 的 gain 里，01B 加的轻度强度惩罚：

```python
gain -= 0.25 * (x["slope"] + x["crowd_level"] * 0.4)
```

南山一棵树：`must_see=True`、`night_friendly=True`、`slope=3`、`crowd_level=3`
→ 惩罚 `0.25 × (3 + 1.2) = 1.05`，把它从 gain 里压了出去。

### 修法（**软约束不该挤掉硬期待**）

强度是**软约束**（超出只提示、不阻断），它不应该挤掉：
- **`must_see` 的必游地标** —— 用户期待的核心，不该被软约束淘汰
- **夜间体验点** —— 夜游本身就是成渝线路的核心卖点，"因为坡陡所以不去看夜景"是荒谬的

改法：

```python
# 强度惩罚只作用于「既非必游地标、又非夜间体验点」的候选
if not x.get("must_see") and not x.get("night_friendly"):
    gain -= 0.25 * (x["slope"] + x["crowd_level"] * 0.4)
```

其余（距离惩罚 `-2.0×leg`、夜间加分 `+0.8`、偏好分）**保持不变**。

### 预期结果（Default 场景）

Day 3 应回到 4 个点、**南山一棵树 19:00–20:30 夜景收尾**，
强度回到 12.2 → 触发 **soft** advisory → 校验段第 1 轮 `✔ 硬约束零违规；另有 1 条软提醒`。

**两个都要**：夜景收尾 + 一次诚实的软提醒（"强度是软约束，自动删点会误伤必游地标，故保留行程并提示"）——
这比"删点凑阈值"有品位得多，也是答辩时能讲的一句话。

### 测试要求（现有测试太弱，必须加强）

现有 `test_intensity_penalty_keeps_must_see` 只断言"重庆 must_see 点集与行程点集有交集非空"，
重庆有 3 个 must_see（长江索道/洪崖洞/南山一棵树），摘掉 1 个断言照样通过 —— **它没抓住这个问题**。

并新增一个**夜景收尾**断言：默认场景下**至少存在一个 arrival ≥ 19:00 的 poi**，
且当天的叙事文案提到夜景时，当天确实有夜景时段的点（**文案与行程一致**）。

## 问题 2（必须修）：`_trim_to_capacity` 的摘点排序键写反了

### 现象

`server/agent/planner.py` 的 `_trim_to_capacity()`：

```python
drop_rank = sorted(kept, key=lambda p: (p.get("_score", 0), not p.get("must_see", False), not p["night_friendly"]))
```

- `must_see=True` → `not must_see` = `False` = 0 → 排**最前** → **最先被摘**
- `night_friendly=True` → `not night_friendly` = `False` = 0 → 排**最前** → **最先被摘**

与规格相反。规格是：「低分先摘；**同分时优先摘非 must_see、再优先摘非夜间点**」。

### 为什么会漏掉

现有测试 `test_trim_to_capacity_drops_low_score_keeps_must_night` 里 `_score` 被手工设成
0.5 / 1.0 / 9.0 / 8.0 **各不相同**，主键就分出了胜负，**次级键从未参与比较**。
平分场景没有覆盖。

目前 trim 在默认场景不触发，所以这是**潜伏 bug**——但一旦在别的参数组合下触发，
它摘掉的就是**最该保的地标**（必游 + 夜间），正好是问题 1 想保护的那类点。

### 修法

```python
drop_rank = sorted(kept, key=lambda p: (p.get("_score", 0),
                                         p.get("must_see", False),
                                         p.get("night_friendly", False)))
```

升序排序下：`must_see=False(0)` 排在 `must_see=True(1)` 之前 → **非必游先摘**；
`night_friendly=False(0)` 排在前面 → **非夜间先摘**。与规格一致。

### 测试要求

新增一个**同分**场景的用例：构造若干 `_score` **完全相同**、但 `must_see` / `night_friendly` 不同的点，
断言摘掉的是「非必游且非夜间」的那个，必游与夜间点都保留。
（注意：`_score` 相同 → 必须显式构造，不能像现在这样手工设成不同值。）

## 问题 3（可选，做了更好）：夜景点可能被排在"不是夜的"时段

`_order_day()` 只保证 `night_friendly` 的点排在**最后**，不保证它落在**夜晚**。

实测：洪崖洞 `crowd_peak=[19,22]`（19 点亮灯才是精华），却被排在 **16:39–18:39**——
白天看的是没亮灯的吊脚楼。有南山一棵树兜底时观感尚可，但它本身的观赏价值被打了折。

建议（**可选，不做也不阻塞**）：在 `_build_timeline()` 里，遇到 `night_friendly` 的点时，
把它的到达时间下限设为该点的最佳观赏时段起点（用 `crowd_peak[0]`，洪崖洞 = 19.0），
即 `arrival = max(arrival, crowd_peak[0])` 附近；若因此导致收班超过 22:00，
则**回退**到不推迟的排法（宁可早看，不可晚归）。

若做这一项，必须同步确认：
- 不触发 V1（收班 ≤ 22:00、内容时长 ≤ 容量）
- 5 组参数下 V1 仍零误报
- 时间线上若出现"空等"（如 18:39–19:00），要**显式体现**（例如在 items 里插一条 `type="wait"` 条目或调整晚餐时间），
  **不要让前端渲染出一段无解释的空白**
