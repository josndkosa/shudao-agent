## 缺陷 1（最高优先级）：V1 时长规则在「跨城日」必然误报

### 现象

运行 `python cli.py --days 3 --budget 3000 --tags 美食,文化`，校验段报告：

```
[validate] violation [V1-duration] 第3天  日占用 13.8h 超过容量 11.0h
```

随后规划段"修复"掉了**磁器口**和**湖广会馆**——但这两个点完全合法，当天 20:30 就结束了（远早于 22:00 上限）。

### 根因（已定位，请勿重新猜测）

`server/agent/validator.py` 第 30–39 行：

```python
span = last_dep - DAY_START + (1.8 if has_ic else 0)   # 城际 1.8h 被「加进」占用
cap  = DAY_END - DAY_START - MEAL_HOURS - BUFFER        # = 22 - 8.5 - 2 - 0.5 = 11.0
if span - MEAL_HOURS - BUFFER > cap + 0.01:             # 阈值实际变成 20:13
    violations.append({"rule": "V1-duration", ...})
```

两处口径打架：

1. **城际 1.8h 在 `span` 里加了，但在 `cap` 里没减** → 判定阈值从 22:00 被压到 20:13。
2. **规划器已经把城际时间扣进容量了**。`planner.py` 里：
   ```python
   capacity = (DAY_END - DAY_START - MEAL_HOURS - BUFFER) - (1.8 if switch else 0)
   ```
   即跨城日的可用内容时长只有 `11.0 - 1.8 = 9.2h`，城际 1.8h 已经被正确预留过。

所以这条规则在跨城日永远误报，且会把合法点位误删。非跨城日则退化成与上面那条 `last_dep > DAY_END` 完全重复的判断。

### 要求

让 V1 的判定与规划器的容量模型**完全一致**，具体：

- 判定依据改为「**实际内容时长 vs 规划器同款容量**」：
  - 内容时长 = `sum(it["leg_hours"] + it["visit_hours"] for it in poi_items)`（`leg_hours` 已在 timeline item 里；缺失时按 0 处理，用 `.get()`）
  - 容量 = `(DAY_END - DAY_START - MEAL_HOURS - BUFFER) - (1.8 if has_ic else 0)`
- 保留原有 `last_dep > DAY_END` 那条判断（收班时间硬上限），但**不要**再重复报一条等价的"日占用"违规。
- 违规 detail 要写清楚是哪种超标（内容时长 vs 收班时间），格式保持 `[rule] 第N天` + 一句中文说明。
- 保留 `fix_hint: "drop"` 字段，前端依赖它。

### 验收

```bash
python cli.py --days 3 --budget 3000 --tags 美食,文化
```

- 第 3 天**不再**出现 V1-duration 违规；
- **磁器口、湖广会馆仍在行程里**；
- 仍然会报 V3-intensity（强度 12.2 > 8.5 上限，这是真实违规，**不要**动它的判定）。

## 缺陷 2：`days=1` 会生成 2 天行程

### 现象

`python cli.py --days 1 --budget 2000` 输出 **2 天**（成都 1 天 + 重庆 1 天）。

### 根因

`server/agent/planner.py` 的 `_allocate_days`：

```python
if days <= 1 or len(cities) <= 1:
    return {c: days for c in cities} if cities else {}
```

`days == 1` 时给**每个**有候选的城市都分 1 天 → 总天数 = 城市数。

### 要求

- `days == 1` 时，**只选一个城市**（选候选池总分更高的那个），只生成 1 天。
- `days >= 2` 时行为保持不变（按候选池总分比例分配）。
- 事件流里"城市分天"那条决策事件的 `reason` 要能说明为什么选了这一个城市（例如"候选池总分更高"）。

### 验收

- `python cli.py --days 1 --budget 2000` → 恰好 1 天；
- `python cli.py --days 3 ...` → 仍是 3 天，城市分配比例不变。

## 缺陷 3：在线模式（`SD_LLM_MODE=online`）必定抛 KeyError

### 现象

`planner.llm_plan()` 直接返回 LLM 生成的 JSON，但 LLM 的 system prompt 只要求它输出 `days/items/budget`，
**没有 `load` 字段**。而 `validator.validate()` 第 64 行：

```python
tickets_total = sum(d["load"]["tickets"] for d in plan.get("days", []))
```

→ `KeyError: 'load'`。而且 `pipeline.run_pipeline` 里校验段没有 try 包裹，异常会直接冒出 CLI。

### 要求

1. **在 `planner.llm_plan()` 里加一个归一化步骤**（例如 `_normalize_llm_plan`），把 LLM 返回的 JSON 补全成离线规划器同构的结构：
   - 每天补齐 `day` / `city` / `weather` / `items` / `load`
   - `items` 里每条至少含 `type`（`poi`/`meal`/`intercity`）、`poi_id`、`name`、`arrival`、`departure`、`visit_hours`、`ticket`、`leg_hours`、`tags`
   - `load` 用 `validator` 同样的口径算：`hours` / `intensity` / `tickets`
   - 缺失或非法的 POI id 一律丢弃（宁可少排也不要让整条管线崩）
   - 如果 LLM 返回的 `days` 为空或无法解析 → 直接降级到 `offline_plan()`（现有逻辑已支持）
2. **在 `pipeline.run_pipeline` 里给校验段加防御**：校验异常不应让整条管线崩溃，应发一条 `validate` / `fallback` 事件并继续（宁可如实标注，也不白屏）。
3. `narrator.narrate` 的在线分支也做同样的保护（它已有 try，但 `msg.content` 为 None 时会 AttributeError，请一并兜底）。

### 验收

- 新增测试：构造一个**不含 `load` 字段**的假 LLM 计划（模拟 LLM 输出），喂给归一化函数，断言产出的结构含 `load` 且 `validator.validate()` 不抛异常。
- 新增测试：LLM 返回 `{"days": []}` 时，`llm_plan` 降级到离线规划器，且事件流里出现 `plan/fallback` 事件。

## 缺陷 4：杂项

1. `pipeline.py` 第 54–69 行的 `for ... else: pass` 是死代码（循环体内所有分支都会 break），请删除。
2. `events.py` 的 `reset_bus()` 从未被调用，`_seq` 是模块级全局计数器 → 同一进程内多次跑管线时事件序号会持续累加。
   - 要求：`EventBus` 实例化时重置该实例自己的 seq 基准（`seq` 从 1 开始），但**不要**破坏跨实例的时间戳 `t`。
   - 注意 `events.py` 里 `_seq` / `_t0` 是模块级私有变量，`reset_bus()` 是公开 API，请在保持 `reset_bus()` 可用的前提下改造。
