# 给码道的下一条任务单：让用户能用一句话开始规划

> 这条整段粘给码道（IDE 模式）。
>
> 前置：03H 那轮（初筛收口）应该已经做完了 —— 四层口径统一、单跑改造、首页数字动态化、
> `load_city_pois` 自动索引、公网防护、03F 剩下的 B–F。如果 03H 还没落地，**先做 03H**。

先说这个功能为什么现在做。

我们现在的规划入口是一个表单：天数、预算、偏好标签、城市多选、亲子勾选。功能上没问题，
但**它不像一个"智能体"该有的样子**——用户得先理解我们的参数长什么样，才知道怎么提需求。
真实用户脑子里装的是一句话：「我在北京，想去成都和重庆玩三天，喜欢美食」。

我们其实已经有一个"听懂人话"的能力了 —— `revise.py` 里的对话式改行程，它能从
「第二天太赶」里解析出「目标天 = 第 2 天、动作 = 减载」。**那套意图解析能力是现成的，
只是用在了"改行程"上，没用在"开始规划"上。**

所以这条任务就是：**把同一个能力接到入口上**。而且和上一轮 03H 一样，
架构上要坚持一条原则 —— **抽取和规划分开**。

```
用户输入一句话
    ↓
【抽取】自然语言 → 结构化参数        ← 这条要新增的，就一层
    {origin, cities, days, budget, tags, family}
    ↓
【规划】现有三段式管线               ← 一行都不用改
    规划 → 校验 → 叙事 → 事件流 → 前端
```

为什么坚持分开，有四个理由，我希望你在代码注释里也写清楚：

1. **抽取是纯理解任务，LLM 强项；规划是约束求解，规则引擎强项。** 混在一个提示里两边都做不好。
2. **抽取结果要回填到参数条让用户看见。** AI 把你的话理解成什么样，你得能看见、能改。
   看不见的话，用户怎么知道 AI 误解了？黑盒是最不可信的设计。
3. **抽取层同一接口两种实现，离线也能用。** 断网保命这条设计不能破。
4. 这跟 `revise.py` 已确立的"意图解析与执行分离"是同一套思路，跟数据层的 Provider 抽象也是同源的。

---

## 几个设计上的选择，我先把我的想法说了，你可以反对

### 抽取结果要回填，不要直接跳到规划

我倾向于**说一句话 → 参数条被填好 → 自动开始规划**，而不是"说一句话 → 直接出结果"。

差别只在前端多一步回填，但多了一层可见性和可纠错性。对评委来说，
"AI 把我说的填进表单，我能看见并修改，然后它才开始规划"比"AI 直接给我结果"更可信。

如果你觉得回填那一步打断流畅感，可以改成回填完**不等用户点**、直接开始规划 —— 参数条上仍然显示
被填上的值，用户随时能改。这个取舍你来定。

### 抽取的结果要**回填**，不是**替换**

参数条上原来有的值，如果抽取没识别出来（比如用户只说了"成都重庆"，没说预算），
**保留原值**，不要清空。用户改过的参数不该被一句话抹掉。

### 离线也要能抽取

抽取器的离线实现（正则 + 词表）不是"降级凑合"，它跟在线实现**同接口**，
所以前端的回填逻辑一行都不用分叉。

### `origin`（出发城市）这一轮只抽取、不计算

你的出发点是"我在北京"。这一轮我们**只把这个词抽出来显示出来**，
**但不把它算进行程时间、不算交通费** —— 因为算准需要全国范围的城市枢纽数据和干线方式判定，
那是下一版的事。

界面上要**如实标注**：「出发地：北京（暂未计入行程时间与交通费）」。
不要让用户以为已经算进去了。

## 具体做什么

### 一、抽取器：新开一个模块，两种实现共用一个函数签名

新建 `server/agent/parse_request.py`：

```python
def parse_request(text: str, bus: EventBus) -> dict:
    """自然语言 → 结构化规划参数。

    返回 {origin, cities, days, budget, tags, family, source, note}
    source: "llm"（在线抽取） | "rules"（离线抽取） | "fallback"（完全没解析出来）
    """
```

**在线实现（LLM）**：

- 用 `llm_mod.chat` 发一次请求，让它输出**纯 JSON**。不要让它解释、不要 markdown 代码块。
- schema 明确：`origin`（字符串，可空）、`cities`（字符串数组）、`days`（整数）、
  `budget`（整数）、`tags`（字符串数组）、`family`（布尔）
- **城市名必须校验**：只接受 `meta.json` 的 `city_info` 里有的城。不认识的城市名过滤掉，
  并在 `note` 里**如实提示**（比如"暂不支持新疆，下次说成都或重庆"）
- **标签必须走 `expand_tags()` 归一到受控词表**（`server/tools/poi_search.py`），
  不让模型自造标签 —— 模型自造标签等于自造语义，后面打分全歪
- **天数 clamp 到合理区间**（比如 1–30），**预算 clamp 到 ≥ 500**
- 模型返回非法 JSON 或调用失败 → **降级到离线实现**，`source` 标 `"rules"`

**离线实现（规则）**：

- 天数：正则 `([0-9一二三四五六七八九十]+)\s*天`
- 预算：正则 `([0-9]+)\s*(元|块|rmb|￥|¥)`
- 城市：文本里匹配 `meta.json` 的 `city_info` 的全部键名（**也要能认别名**，
  比如"重庆/渝"、"成都/蓉"、"昆明/春城"——别名表放 `meta.json` 里，别硬编码在这层）
- 标签：匹配 `meta.json` 的 `tag_aliases` 的全部键
- 亲子：命中「亲子 / 带娃 / 孩子 / 小孩 / 老人」
- 出发地：命中「我在X / 从X出发 / 出发地X / X出发」→ 记为 `origin`（**只记录**）
- 什么都没抽到 → 返回默认值，`source` 标 `"fallback"`

两个实现**必须返回完全同构的结果**，前端不区分来源。

**抽取过程要发事件**（stage 用 `system` 或 `plan`），reason 写清楚读到了什么，
比如「从你的话里读到了：3 天 / 预算 3000 / 成都、重庆 / 美食」。
这是「每条决策带 reason」内核的延伸 —— 用户也得看得见 AI 的理解。

### 二、后端加一个端点

`server/app.py` 新增：

```
POST /api/parse   {"text": "..."}  →  {origin, cities, days, budget, tags, family, source, note}
```

契约写进 `docs/API.md`。返回里**不要带任何不在 schema 里的字段**，前端按固定结构读。

### 三、前端：复用已有的对话栏

`static/plan.html` 和 `static/js/main.js`：

**没有计划的时候**，对话栏的语义是「规划」；**已经有计划了**，语义是「改行程」（走现在的
`/api/revise`，逻辑不许变）。用 placeholder 告诉用户当前是哪种模式：

- 无计划：「说说你想怎么玩，例如：我在北京，想去成都和重庆玩3天，喜欢美食和夜景」
- 有计划：「和规划师说点什么，例如：第二天太赶」

发送时，**如果还没有 plan_id**：

1. 调 `/api/parse`
2. **回填参数条**：`p-days` / `p-budget` / `p-tags` / `p-family` / `p-cities` 的勾选状态
3. **自动触发规划**（或者等用户点"开始规划"，见前面的取舍）
4. 在对话栏回一条：「我理解为：3 天 / 预算 3000 / 成都、重庆 / 美食，已按这个规划
   （可在上方参数条修改）」

**如果抽取失败或返回空**：如实提示「没太看懂，你也可以直接用上方参数条填写」，
**不要报错、不要清空现有参数**。

回填完记得调 `updateCityDayHint()`，让"已选 N 城但只有 M 天"那个提示跟着更新。

`origin` 的展示：参数条加一行只读提示，**如实写明它还没参与计算**。

### 四、天数上限：前后端一起放开

现在有两个地方卡着 7 天：

| 位置 | 现在 |
|---|---|
| `server/app.py` | `days: int = Field(3, ge=1, le=7)` |
| `static/plan.html` | `<input id="p-days" type="number" min="1" max="7" value="3">` |

**两个都要改**，漏一个就是"改了没生效"。上限放到 30。

同时有两个连带缺陷要一起修：

**第一个是静默截断。** `planner.py` 里 `if not picked: continue` ——
某个城的候选点用完了，那一天会被**整个丢掉，而且没有任何事件说明**。
用户要 7 天可能只拿到 5 天，界面上看不出来。改成**发事件**，
reason 写「XX 市候选点已用尽，无法再安排第 N 天」，并且**那天不要占用 day 序号**。

**第二个是预算分母用错。** 预算计算传的是 `request.days`（请求天数），
但城际费用算的是**实际行程天数**。一旦发生上面那种截断，日均花费就被系统性低估。
改成按**实际行程天数**算。

**还有一条物理约束要如实告诉用户**：一个城市每天消耗 4 到 5 个点，所以单城能撑几天
由它的 POI 密度决定（成都 22 个点，大概 4–5 天）。**放开上限不等于任何天数都排得出来。**
请在 `docs/开发指南.md` 里写清这条数据规模约束，前端 `p-days` 附近也加一句提示 ——
别让用户设了 20 天结果只拿到 6 天还一头雾水。

## 验收标准

**抽取层**

- `parse_request("我在北京，想去成都和重庆玩3天，预算3000，喜欢美食和夜景")`
  返回 `{origin: "北京", cities: ["成都","重庆"], days: 3, budget: 3000, tags: ["美食","夜景"], family: false}`
- 同一句话在**离线**（没 key）下抽出**同样的结构**，`source` 是 `"rules"`
- 「我在新疆」→ 新疆不在 `city_info` → 被过滤 + **有如实提示**
- 「带娃去成都玩5天」→ `family: true, days: 5`
- 「预算800块」→ `budget: 800`（数字被抽出来了）
- 模型返回非法 JSON → **降级到规则实现，不抛异常**
- 所有 tags 都落在 `expand_tags()` 的受控词表内（**断言无一例外**）

**前端**

- 无计划时输入一句话 → 参数条被回填 → 自动开始规划 → 对话栏有"我理解为…"那条提示
- 有计划时输入「第二天太赶」→ **走现有 revise 路径，行为零变化**
- 抽取失败 → 如实提示 + **不报错、不清空参数**
- 出发地的提示语里含「暂未计入行程时间与交通费」

**天数放开**

- `--days 12` 能跑出 **≥ 10 天**的行程，且**没有**静默丢天的事件
- 某个城候选点用尽时**有事件**说明
- 预算日均 = 总花费 ÷ **实际行程天数**（断言一致）

**回归**

- `python scripts/ctl.py ci` 三连全绿，pytest 至少 92 个（03H 之后 ≥90，加上本轮的新增），
  冒烟至少 18 步
- **离线基线不变** —— `python cli.py --days 3 --budget 3000 --tags 美食,文化` 的输出
  和 `docs/baseline/baseline-cli-3d.txt` 一致。如果因为改了餐数口径之类有变化，
  **在 CHANGELOG 里写明并更新 baseline 文件**，别让两者悄悄对不上
- 冒烟加至少一步："回填之后参数条被正确填写"的 DOM 断言

⚠️ 抽取器是 Python 写的，**没法在 Node 冒烟里直接测** —— 它的用例应该放在 `tests/` 里用 pytest 覆盖，
冒烟只管前端那一步。别为了能测就把 Python 逻辑挪到前端。

## 有几件事别做

- **别让抽取层决定去哪个 POI。** 抽取只产出参数，点位永远由管线决定。
  一旦抽取能直接指定 POI，厚字段决策依据（开放时段/人流/爬坡强度）就被绕过了，
  整套规则的立论就没了。
- **别在抽取里推断天气、票价、开放时间。** LLM 编这些是要出事的，
  而且我们的原则是"事实来自数据层，不来自模型"。
- **别把表单入口删掉。** 表单是断网保命的兜底，也是抽取失败时的退路。
- **别实现出发城市的交通计算。** 这一轮只抽取和如实标注，计算留给下一版。
- **别把 `SD_LLM_MODE` 的默认值改成 online。**
- 别引新依赖，别顺手重构 `server/agent/` 里跟本轮无关的模块。

做完报一下：抽取器在离线和在线两种模式下分别抽出了什么、
`--days 12` 实际跑出来几天、有没有触发"候选点用尽"的事件、pytest 涨到多少。
