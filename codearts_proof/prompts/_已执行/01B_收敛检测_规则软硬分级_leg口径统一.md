## 问题现场：违规回流修复在默认场景里空转了三轮

`python cli.py --days 3 --budget 3000 --tags 美食,文化` 的真实事件流（见 `docs/baseline/baseline-cli-3d.txt`）：

```
 #017 [validate] ✗ [V3-intensity] 第3天
      └ 因为 强度 12.2 超过 8.5
 #018 [plan    ] ↻ 第1轮修复回流规划段
 #019 [plan    ] ↻ 第3天强度超标，保留原行程
 #020 [validate] ✗ [V3-intensity] 第3天          ← 与 #017 完全相同
 #021 [plan    ] ↻ 第2轮修复回流规划段
 #022 [plan    ] ↻ 第3天强度超标，保留原行程      ← 与 #019 完全相同
 #023 [validate] ✗ [V3-intensity] 第3天          ← 与 #017 完全相同
 #024 [validate] ■ 校验结束（仍残留违规，如实标注）
```

**为什么**：Prompt 01 把 V3 的自动修复改成了"如实标注、不删点"（这个改动本身是对的，见下），
于是 `planner.fix()` 对 V3 变成 no-op → 每轮违规集合完全相同 → 循环白白跑满 3 轮。

**为什么这是演示缺陷，不是代码细节**：

1. 「**违规回流修复**」是本作品的核心卖点之一（README 架构图第一行就是"↕ 违规回流修复"）。
   评委在可倒带时间轴上拖动进度条，会看到"发现问题 → 修复 → 还是这个问题 → 修复 → 还是这个问题 → 放弃"，
   这读起来是**校验段无能为力**——恰好打在卖点上。
2. 时间轴后三分之一是三段一模一样的文本，视觉上很难看。

**但请注意**：Prompt 01 把 V3 改成"不删点"是**正确的工程判断**，不要回退。
理由：强度是软约束，删哪个点都是错的（南山一棵树是必游夜景机位，磁器口是核心景点），
"删点凑阈值"本身就是个糟糕的产品决策。**要改的是"软约束不该占硬违规的名额"，不是"把删点的逻辑加回来"。**

## 任务 A（必做）：规则软硬分级，软约束不进回流循环

### A1. `validator.validate()` 给每条违规加 `severity` 字段

```python
{"rule": "V1-duration", "severity": "hard", ...}   # 硬约束：必须自动修复
{"rule": "V3-intensity", "severity": "soft", ...}   # 软约束：只提醒，不自动修复
```

分级：

| 规则 | severity | 理由 |
|---|---|---|
| V1 时长 | `hard` | 违反物理时间边界，必须修 |
| V2 开放窗口 | `hard` | 景点没开门，去了就是白跑，必须修 |
| V4 预算 | `hard` | 超出用户预算是承诺问题，必须修 |
| V5 亲子 | `hard` | 亲子友好度不达标是安全问题，必须修 |
| **V3 强度** | **`soft`** | 没有唯一正确的删点解；系统应如实提示、把决策权交还用户 |

**保持 `validate()` 的返回结构不变**（仍是 violations 列表），只多一个 key。
`fix_hint` 字段保留。

### A2. `pipeline.run_pipeline()` 按 severity 分流

```
hard = [v for v in violations if v["severity"] == "hard"]
soft = [v for v in violations if v["severity"] == "soft"]
```

- **soft** → 发 `stage="validate", type="advisory"` 事件（**不进修复循环**），
  title 形如 `[V3-intensity] 第3天`，reason 写清数值与阈值 + 一句产品判断，例如：
  `强度 12.2 超过 8.5；强度是软约束，自动删点会误伤必游地标，故保留行程并提示`
- **hard** → 进原有的「修复回流」循环
- **「校验通过」的判定只看 hard**：没有 hard 违规就发 `validate/pass`，
  reason 写「硬约束零违规」；若同时有 soft 提醒，追加一句「另有 N 条软提醒（已如实标注）」

改完之后，默认场景的事件流应该是这样的形状（**没有重复的空转**）：

```
 #017 [validate] ⚠ [V3-intensity] 第3天
      └ 因为 强度 12.2 超过 8.5；强度是软约束，自动删点会误伤必游地标，故保留行程并提示
 #018 [validate] ✔ 第1轮校验通过
      └ 因为 硬约束零违规；另有 1 条软提醒（已如实标注）
```

### A3. 新增事件类型（前端 Prompt 03 会消费）

| type | 用途 | 建议图标 |
|---|---|---|
| `advisory` | 软约束提醒，不阻断 | `⚠` |
| `unfixable` | 硬违规存在但无自动修复策略 | `⊘` |

## 任务 B（必做）：修复循环的收敛检测

即使全是 hard 违规，也可能出现"修了但没修好"的情况。请在 `pipeline` 的循环里加收敛检测：

1. 记录本轮进入循环前的 hard 违规集合（用 `(rule, day, poi)` 三元组构成的集合）
2. 执行 `planner.fix()` 后进入下一轮，重新校验
3. 若新的 hard 违规集合与上一轮**完全相同**（说明 fix 没改变任何东西）→ 立即跳出循环，
   发一条 `stage="validate", type="unfixable"` 事件，reason 如实写明
   「该违规无可用自动修复策略，修复后状态未变，已停止重试」
4. **绝不重复空转**。宁可 1 轮结束并如实标注，也不要 3 轮一模一样的文本。

## 任务 C（必做）：规划器与校验器的 leg 口径统一（**修同一类 bug 的复发**）

### 现状：两把不同的尺子，只差 1.5%

- **规划器** `_pick_day_pois()` 装箱时用**质心跳**估交通：`leg_time(center, x)`（center = 已选点的平均坐标）
- **校验器** `validator.validate()` 用**时间线实际跳**：`it["leg_hours"]`（相邻两点之间的真实耗时）
- **时间线** `_build_timeline()` 也是用相邻跳

质心跳 ≠ 相邻跳，规划器算出来的占用**偏乐观**，所以它会把箱子填得比校验器允许的更满。
当前默认场景的余量实测：

| 天 | content_hours | cap | 余量 |
|---|---|---|---|
| Day 1 成都 | 10.85 | 11.0 | **0.15h** |
| Day 3 重庆（跨城） | 9.06 | 9.2 | **0.14h** |

只剩约 1.5%。**换一组参数（例如 `--days 2 --tags 亲子` 或 `--budget` 变化）就可能翻过去，再次触发 V1 误报**
——和我们刚修掉的 D1 是同一类 bug，只是这次在别的参数组合下发作。

### 要求：让规划器用校验器同一把尺子复核

1. 在 `_order_day()` **排序之后**、构造时间线之前，用**相邻跳**的真实值计算该日内容时长：
   ```
   content = Σ( p["visit_hours"] + leg_time(prev, p) )   # prev 从 CITY_HUB[city] 起算
   ```
   这与 `validator` 的 `content_hours` 口径完全一致（timeline item 的 `leg_hours` 就是这么算的）
2. 若 `content > capacity`（capacity 与规划器现用的一致：`(DAY_END - DAY_START - MEAL_HOURS - BUFFER) - (1.8 if 跨城 else 0)`），
   **摘点直到 content ≤ capacity**：
   - 候选顺序：先摘 `_score` 低的；同分时优先摘**非 `must_see`**、再优先摘**非夜间点**
     （夜间点是压轴体验，磁器口/洪崖洞/南山一棵树这类必须优先保住）
   - 每次摘点后**重新计算** content，直到满足容量
   - **不允许**摘到该天一个点都不剩
3. 摘点必须在 `bus.emit("plan", "decision", ...)` **之前**完成，
   让事件流里的「第N天选点 X 个」就是最终结果，不出现"先说 4 个后来变成 3 个"的错位

### 验收

- `python cli.py --days 3 --budget 3000 --tags 美食,文化` → **无 V1-duration 违规**
- `python cli.py --days 2 --budget 2500 --tags 亲子,遛娃 --family` → **无 V1-duration 违规**
- `python cli.py --days 2 --budget 2000 --tags 夜景` → **无 V1-duration 违规**
- 至少 5 组不同参数组合下，validator 报出的 V1 与"规划器自算的内容时长"**完全一致**（不出现规划器认为不超、校验器认为超）

## 任务 D（可选，做了更好）：装箱时加轻度强度惩罚

当前重庆天强度 12.2（南山一棵树 slope3 + 洪崖洞 slope1/crowd5 + 磁器口 slope1/crowd4 + 湖广会馆 slope2/crowd1）。
成都天只有 5.6/5.8。**用同一把强度尺子衡量两城并不合理**——重庆的坡是城市特色本身。

建议在 `_pick_day_pois()` 的 `gain` 里加一个**轻度**强度项（不硬约束，只影响排序）：

```python
intensity_delta = x["slope"] + x["crowd_level"] * 0.4
gain -= 0.25 * intensity_delta      # 系数自行调，但保持"轻度"——不要让它压过偏好分
```

效果：重庆天会自然少排一个爬坡点，或换成体验相近但更平缓的点。
**约束**：`gain` 里的距离惩罚（`-2.0*leg`）和夜间加分（`+0.8`）保持不变；
强度惩罚**不得**导致任何一天出现"被摘光的必要地标"。

做完请对比 `--days 3 --budget 3000 --tags 美食,文化` 的重庆天：点位数量、强度值、是否还含洪崖洞/南山一棵树。
**如果强度降到 8.5 以下 → 软提醒消失，V3 这条软规则在默认场景就不会触发**，
这是好事，但要在回复里说明（PPT 的叙事需要知道默认场景有没有软提醒）。
