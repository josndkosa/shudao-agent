## 问题一：Day 标签横向拖不动

### 现在的样子

30 天 + 6 个城市会生成 24 个 Day 标签。截图里它们从 `Day 1 · 丽江` 一直排到 `Day 24 · 重庆`，
**一行铺开、超出容器，然后拖不动**。

### 根因

`static/style.css` 第 338 行：

```css
.day-tabs { display: flex; border-bottom: 2px solid var(--ink); animation: drawX .34s var(--ease-out) 900ms both; transform-origin: left; }
```

**`display: flex` 但没有 `overflow-x: auto`。**

对比同一个文件第 221 行的 `.map-row`：

```css
.map-row { display: flex; overflow-x: auto; scrollbar-width: thin; border-bottom: 1px solid var(--rule); }
```

`map-row` 有、`.day-tabs` 没有 —— **两个横向滚动区域只改了一个，漏了另一个。**

没有 `overflow-x` 的话，flex 子项会**撑破容器**，整个页面跟着横向溢出。

### 修法

**第一步，给 `.day-tabs` 补上横向滚动：**

```css
.day-tabs {
  display: flex; overflow-x: auto; scrollbar-width: thin;
  border-bottom: 2px solid var(--ink);
  animation: drawX .34s var(--ease-out) 900ms both; transform-origin: left;
  scroll-behavior: smooth;
}
.day-tab { flex: 0 0 auto; }   /* 不许被压缩，否则标题会被挤断 */
```

`flex: 0 0 auto` 很重要 —— 不加的话 flex 会尝试压缩每个标签，文字被挤成竖排。

**第二步，滚动条要看得见。** 现在的设计语言是"发丝线"，滚动条太粗会破坏版式，
但**完全看不见用户就不知道能滚**。用细滚动条，样式跟 `.map-row` 保持一致：

```css
.day-tabs::-webkit-scrollbar { height: 6px; }
.day-tabs::-webkit-scrollbar-thumb { background: var(--ink3); border-radius: 0; }
.day-tabs::-webkit-scrollbar-track { background: transparent; }
```

**第三步，"拖动"这个动作要真的能用。**

`overflow-x: auto` 支持**触摸板横滑**和**Shift + 滚轮**，但**不支持鼠标按住内容直接拖**。
用户说"拖动滑动不了"，多半就是试了直接拖。所以要加拖拽滚动。

抽成一个通用函数，`.day-tabs` 和 `.map-row` **共用**（现在两个区域都有横向滚动，
各写一遍是重复劳动）：

```js
/** 横向拖动滚动：鼠标按住内容左右拖。触摸设备走原生，不拦截。 */
export function enableDragScroll(el) {
  let dragging = false, startX = 0, startLeft = 0;
  el.addEventListener("pointerdown", e => {
    if (e.pointerType === "touch") return;      // 触摸交给原生
    if (e.target.closest("button, a, input, select")) return;  // 别抢按钮的按下
    dragging = true; startX = e.clientX; startLeft = el.scrollLeft;
    el.setPointerCapture(e.pointerId);
    el.classList.add("dragging");
  });
  el.addEventListener("pointermove", e => {
    if (!dragging) return;
    el.scrollLeft = startLeft - (e.clientX - startX);
  });
  const stop = () => { dragging = false; el.classList.remove("dragging"); };
  el.addEventListener("pointerup", stop);
  el.addEventListener("pointercancel", stop);
}
```

配套的视觉反馈（拖的时候光标变抓手，并且**不要选中文字**）：

```css
.day-tabs, .map-row { cursor: grab; }
.day-tabs.dragging, .map-row.dragging { cursor: grabbing; }
.day-tabs.dragging, .map-row.dragging { user-select: none; }
```

**第四步，加一个"还有更多"的提示。**

`.map-row` 已经有「← 横向滑动查看全部城市 →」这个提示（`map-scroll-hint`），
Day 标签这边也该有一个 —— 现在用户根本不知道右边还有 21 天。
按 `.map-scroll-hint` 的样式照做，**只在标签总宽超出容器时显示**（用 `scrollWidth > clientWidth` 判断，
不要写死"超过 N 个就显示"）。

### 验收

- 30 天 / 6 城 → 24 个 Day 标签，**能横向拖动**，能滚到 `Day 24`
- 拖动时鼠标是抓手形状，**不会选中标签文字**
- 滚动条细但**看得见**
- 标签文字**不被压缩变形**（`Day 12 · 昆明` 要完整显示）
- **页面本身不出现横向滚动条**（`.layout` 之外不能有溢出）
- 切天仍然正常（点哪个 tab 就切到哪一天）

## 问题二：对话栏太靠下

### 现在的样子

`.chat-bar` 是 `position: fixed; left: 0; right: 0; bottom: 0` ——
**一条全宽的横条永远压在视口最底下**，输入框在页面最下面那条线上。

用户反馈是「位置太往下了，观感上不习惯不美观」。

### 我的判断

这个位置确实别扭，而且有两个连带问题：

1. **一条 2px 黑边全宽压在底边**，把页面"切断"了 —— 视线被强制拉到最下面
2. `.layout` 的 `padding: 0 32px 24px` **没有给这个 fixed 条留底部空间**，
   内容有被压住的隐患（现在靠行程恰好够长躲过去了）

### 修法：把它移到参数条下面

**对话和参数本来就是一件事** —— 都是"用户的输入"。现在参数在上面、对话在下面，
中间隔了一整个地图和行程，语义上是割裂的。

具体做法：

**DOM 层面**：把 `<footer class="chat-bar">` 从 `</body>` 前面挪到
**`.params` 之后、`.map-row` 之前**，作为 `<main class="left">` 里的一个独立节点。

⚠️ **不要放进 `<form id="params-form">` 内部。** 参数条的表单绑定了 submit 事件，
对话输入框在里面的话，按回车会**提交表单触发规划**，而不是发消息。
放在 form 外面最安全。

**CSS 层面**：去掉 fixed，改成普通的文档流块：

```css
.chat-bar {
  /* 去掉 position: fixed; left/right/bottom; z-index */
  display: flex; align-items: center; gap: 12px;
  padding: 14px 0 16px;
  border-top: 1px solid var(--rule);
  border-bottom: 1px solid var(--rule);
  background: var(--bg);
}
```

**保留** `.chat-hint`（"试试：" + 快捷句）、`.chat-note`（"我理解为…"）、
`.chat-input`、`.btn-primary` 这些现有结构和样式，**只改位置和定位方式**。

**页面底部**因此不再被一条横条切开，`.layout` 的底部 padding 也就自然了。

### 如果你想更省版面

另一个方案是**右下角悬浮胶囊**：默认只显示一个圆形按钮，点开才展开输入框。
优点是几乎不占版面，缺点是"对话入口"不够显眼，而答辩现场要让人一眼看到能说话。

**我推荐上面那个「移到参数条下方」的方案**，因为它更符合工作台的形态，
而且 03G 刚做完的"自然语言入口"本来就该在这个位置 —— 现在算是把位置摆正了。

如果你更想要胶囊方案，跟我说一声，我把这一节换掉，其他两节不变。

### 验收

- 对话栏**紧跟在参数条下面**，在地图上面
- **页面底部不再有固定横条**，滚到底部时对话栏不会挡住任何内容
- 对话输入框按回车**发消息**，不触发规划
- 参数条里的"开始规划"按钮行为不变
- "试试：xxx"那三个快捷句仍然能点、能填进输入框

## 问题三：Day 编号跳号（Day 1,2,3,4,**6**,7,8,9,**11**…）

### 现在的样子

截图里的 Day 标签是：`Day 1 · 丽江`、`Day 2 · 丽江`、`Day 3 · 丽江`、`Day 4 · 丽江`、
**`Day 6 · 大理`**（**5 跳了**）…

一直到 `Day 24 · 重庆`，中间跳过了 5、10、15。

### 根因

在线路径里，`server/agent/planner.py` 第 512 行：

```python
"day": d.get("day") or i, "city": city,
```

**天号用的是 LLM 返回的 `day` 字段。**

模型返回了 24 天，其中 3 天（5、10、15）拿到的 poi_id 全部非法，被
`_normalize_llm_plan` 的 `continue` 丢掉了。**但剩下那些天仍然保留着模型给的原号**，
于是编号就出现了空洞。

离线路径没这个问题（`planner.py` 的 `day_no` 是我们自己递增的，丢天就不编号），
所以**只有在线模式会跳号**。

### 为什么必须修

评委看到 `Day 1, 2, 3, 4, 6, 7…` 会以为程序出错了 —— 一天去哪了？
而实际上"那天排不满被丢弃"这件事，我们已经在事件流里如实说明过了，
**编号连续**才能让"编号 = 行程的第几天"这个直觉成立。

### 修法

**天号由我们自己连续分配，不信模型的。**

`_normalize_llm_plan` 里维护一个自己的计数器：

```python
days_out, prev_city = [], None
day_seq = 0                      # ← 我们自己的连续天号
for i, d in enumerate(raw.get("days") or [], start=1):
    ...
    day_seq += 1                 # ← 只给真正产出了这一天的行程编号
    days_out.append({"day": day_seq, ...})
```

**被丢掉的天不占号**，编号就连续了。

模型给的 `day` 字段**可以留作参考**（比如写进 reason 里说明"模型原本安排的是第 5 天"），
但**不作为显示用的天号**。

另外顺手看一眼离线路径的 `planner.py:352` 那个 `if not picked:` ——
它现在丢天的时候**有没有发事件**？03H 任务 H2 说过要发。
如果还没发，这一轮一起补上（reason 写「XX 市候选点已用尽，无法再安排第 N 天」）。
**如果已经发过了就跳过这步。**

### 验收

- 30 天 / 6 城 → Day 标签是 **1, 2, 3, 4, 5, 6 …** **连续无空洞**
- 离线模式的天号**仍然连续**（不能因为改了在线逻辑把离线弄坏了）
- 被丢弃的天在**事件流里有明确说明**（不是静默消失）
- 行程卡片里的"Day N"和 Day 标签上的"Day N"**一致**
- 「第 N 天选点」这类事件的标题里的天号，和行程卡片对得上
