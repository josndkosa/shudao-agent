# 第二轮：软硬分级 + 收敛检测 + 口径统一（2026-10-28 深夜追加）

> 起因：修复循环对 V3（软约束）空转 3 轮——同一违规文本重复 3 遍，打在「违规回流修复」卖点上的演示缺陷。

## 问题：V3 空转

Prompt 01 把 V3 改为"如实标注不删点"后，`planner.fix()` 对 V3 成 no-op → 每轮违规集合完全相同 → 循环跑满 3 轮全是重复文本。工程判断正确（强度是软约束，删点凑阈值是糟糕的产品决策），但软约束不该占硬违规的名额。

## 修复 A：规则软硬分级

- `validator.validate()` 每条违规加 `severity` 字段：V1/V2/V4/V5=hard（必须自动修复），V3=soft（只提醒）
- `pipeline` 按 severity 分流：soft → `validate/advisory` 事件（不进循环）；hard → 修复循环
- 「校验通过」只看 hard：`pass` reason 写「硬约束零违规；另有 N 条软提醒（已如实标注）」

## 修复 B：收敛检测

循环里记录 hard 违规签名集合 `(rule, day, poi)`；fix 后新一轮若签名与上轮完全相同 → 立即跳出，发 `validate/unfixable` 事件（reason：「该违规无可用自动修复策略，修复后状态未变，已停止重试」）。绝不重复空转。

## 修复 C：规划器/校验器 leg 口径统一（D1 同类 bug 复发防治）

- 旧状：`_pick_day_pois` 装箱用**质心跳**估交通（乐观），validator 用**相邻跳**（真实）→ 余量仅 0.15h/0.14h，换参数即翻车
- 修复：新增 `_content_hours()`（相邻跳口径）+ `_trim_to_capacity()`——`_order_day` 排序后、emit decision 之前复核容量，超容摘点（低分→非必游→非夜间优先），不摘光
- **实现 bug 自查**：初版 `_trim_to_capacity` 原地 remove 导致 `trimmed is ordered`（测试 `assert len(trimmed) < len(ordered)` 永假）——改为返回新列表。这个测试抓到了真 bug

## 修复 D（可选，已做）：装箱轻度强度惩罚

`_pick_day_pois` 的 gain 加 `-0.25 × (slope + crowd_level×0.4)`（距离惩罚 -2.0×leg 与夜间加分 +0.8 不变）。

# 第三轮：恢复夜景收尾 + 修正摘点排序键（Prompt 01C，2026-10-29）

> TDD：4 个新用例先红（南山被挤出/同分摘反/文案不一致/默认场景无 advisory），修复后 48 passed（44+4）。

## 问题 1：强度惩罚把南山一棵树挤出装箱

**根因**：01B 的 `gain -= 0.25 × (slope + crowd_level×0.4)` 无差别作用于所有点。南山 slope=3 → 惩罚 -1.05 被挤出 → Day 3 失去夜景收尾，且叙事文案仍写"行程以夜景收尾"（文案与行程自相矛盾，演示级问题）。

**修复**：强度惩罚（软约束）豁免两类硬期待——必游地标与夜间体验点：
```python
if not x.get("must_see") and not x.get("night_friendly"):
    gain -= 0.25 * (x["slope"] + x["crowd_level"] * 0.4)
```
软约束不该挤掉硬期待；"因为坡陡所以不去看夜景"是荒谬的。

## 问题 2：_trim_to_capacity 摘点排序键写反（潜伏 bug）

**根因**：`(score, not must_see, not night_friendly)` 升序下 `not True=False=0` 排最前 → **必游点与夜间点最先被摘**，与规格相反。现有测试 _score 各不相同，次级键从未参与比较。

**修复**：`(score, must_see, night_friendly)` 升序——非必游（0）先摘、非夜间（0）先摘。新增同分场景测试 `test_trim_drop_rank_same_score` 覆盖。

**实现自查**：测试初版前提不足（摘 1 个即够），改为跨城容量（9.2h）迫使摘 2 个，验证了排序键的第二、第三键。

## 附带修复：夜景文案与排班一致性

`narrator._template_narrate` 的"行程以夜景收尾"原先只看 tags 含夜景/夜生活，导致 Day 2（铁像寺 15:03 到达）文案与实际矛盾。改为：**只有 arrival ≥ 18:00 的夜景点才触发该句**。测试断言精确匹配"夜景收尾"四字（避免锦里 summary 里"红灯笼夜景"字样误判）。

# 第六轮：setEvents 未声明标识符——node --check 查不出的那类 bug（2026-10-29）

## 症状与根因

页面打开正常，点「开始规划」后行程区/事件流全空、控制台未捕获异常。根因：`player.js` 的 `setEvents(events)` 签名只有一个参数，函数体却引用了未声明的 `cursor`（F1 修复时一次编辑因 mtime 失败重做，函数体改了、签名行漏改）→ `ReferenceError: cursor is not defined`，`run()` 无 catch → 未处理的 Promise rejection → 白屏。

**为什么打开页面不报错**：boot() 不调用 setEvents，只有点「开始规划」才触发。**为什么 node --check 没抓到**：`--check` 只做语法解析，不做未声明标识符检查（严格说，裸标识符解析在语法层是合法的，只有在运行时求值才抛 ReferenceError）。**为什么三个调用点全炸**：setEvents 在 run() 正常路径、run() catch 兜底、revise() 三处都被调用，一次全灭，且 revise 的 F1 修复（第二个参数 target）被静默丢弃等于没生效。

## 修复

1. 签名补参数：`setEvents(events, cursor = null)`
2. run()/revise() 加可见 catch：错误上顶部徽标红字（新增 .badge-error 样式）——宁可红字报错，不要白屏。答辩现场白屏等于 0 分，红字至少能立刻定位
3. 全量扫描 static/js 五文件：fmtHour/removedNames/setStreaming/revisedDay/_diffDay/_lastItinerary 等新符号的声明与引用逐个核对，拼写全部一致
4. 新增 `scripts/smoke_frontend.mjs`：DOM stub + fetch stub（/api/health 拒绝强制走 Mock 路径，demo*.json 读真实产物），运行时加载 api/player/map/timeline 四模块并执行关键路径（含 `setEvents(events, 1)` 与 `setEvents(events)` 两种签名、CityMaps.render 的 removed 灰叉分支、DayPanel.render 的 removedNames 分支），任何异常非零退出

## 运行时验证（区别于 node --check 的那一次）

- **A 组（后端在场，uvicorn:8000）**：后端日志完整记录 `GET /js/*.js → /api/health 200 → /api/geo 200 → POST /api/plan 200 → POST /api/stream 200`——run() 全链路无异常，SSE 正常建立
- **B 组（后端杀掉，静态 :8765）**：health 探测失败 → MockApi → plan 读 demo.json → setEvents 修复后不再炸

## 被自己的测试/工具抓到的问题（本轮四个）

1. **冒烟抓到 `_city_meta` 污染城市遍历**：demo-geo.json 顶层加元数据键后，`CityMaps` constructor

## 期间发现的既有隐藏 bug（批次1 之外的收获）

写 V3 分档触发统计时发现 advisory 事件的 day 提取不到 → 顺藤摸瓜：
`EventBus.emit(stage, type_, title, reason="", **detail)` 的 kwargs 收集使 `emit(..., detail=v)`
产生**嵌套 detail**（`{"detail": v}`），而前端 `applyEvent` 读 `ev.detail.day` 恒为 undefined——
**01B 引入软提醒以来，行程卡的琥珀提醒条与违规点击高亮从未真正渲染过**（此前验证都停在数据层：
「demo.json 恰 1 条 advisory」✓，但没人断言过「提醒条出现在页面上」）。
修：main.js 兼容取内层（`ev.detail.detail || ev.detail`），不改后端事件结构（demo 资产与回归零影响）。
教训：**验证层级每上一级能抓的 bug 多一类**——这次是「数据层验证 ≠ UI 消费验证」的又一例（与第五/六轮同款）。
